# NESS Relay v2.5.0 — Endpoints Dedicados para Auditoría

**Fecha**: 2026-07-06  
**Binario MD5**: `44a78d0d08a429c2729771ddc32758e5` (7,377,344 bytes)  
**Cambio principal**: separación del payload de auditoría en 2 endpoints dedicados.

---

## Motivación

Hasta la v2.4.0 el agente enviaba toda la información (SNMP + audit) en un único
POST a `/api/relay/data/`. Esto provocaba:

1. **Acoplamiento**: el endpoint SNMP recibía 3 responsabilidades distintas.
2. **Tamaño de payload**: con 16 controles CIS + 2 CVEs por dispositivo, el JSON
   crecía rápido. Con 5 FortiGates eso ya eran ~50 KB por POST.
3. **Idempotencia granular**: si fallaba una parte del payload, había que
   reenviar todo.
4. **Multi-vendor**: al añadir pfSense/MikroTik en el futuro, los volúmenes se
   multiplicaban sin una separación clara.

## Solución v2.5.0

El agente ahora hace **3 POSTs separados** por dispositivo y por ejecución:

| # | Endpoint | Payload |
|---|----------|---------|
| 1 | `POST /api/relay/data/` | Solo telemetría SNMP (sigue como antes) |
| 2 | `POST /api/relay/audit/vulnerabilities/` | Solo bloque `vulnerabilities` del audit |
| 3 | `POST /api/relay/audit/cis/` | Solo bloque `cis_compliance` del audit |

### Beneficios

- Cada endpoint tiene un único schema y propósito → más fácil de versionar.
- Si falla el audit, el SNMP sigue llegando (no se pierde telemetría).
- Si falla el SNMP, el audit igual se persiste.
- Permite rate-limiting independiente por endpoint.
- Backward compatible: si el endpoint dedicado falla, el agente hace fallback
  anexando el bloque al payload SNMP (deprecado, sólo fase de transición).

## Cambios técnicos

### Nuevo módulo: `src/exporters/audit_sender.rs`

```rust
pub enum AuditKind { Vulnerabilities, Cis }

pub async fn send_audit_payload(
    server_url: &str,        // ej. "http://172.206.0.217:8080"
    api_token: &str,
    kind: AuditKind,
    payload: serde_json::Value,
    device_hostname: &str,
) -> Result<AuditSendOutcome, anyhow::Error>

pub fn build_audit_url(server_url: &str, kind: AuditKind) -> String {
    let base = server_url.trim_end_matches("/api/relay/data/");
    let slug = match kind {
        AuditKind::Vulnerabilities => "vulnerabilities",
        AuditKind::Cis             => "cis",
    };
    format!("{}/api/relay/audit/{}/", base, slug)
}
```

El agente deriva la URL base eliminando `/api/relay/data/` de la URL configurada,
así que **no hay que cambiar `connection.config`** — sólo actualizar el binario.

### `src/core/engine.rs`

Antes (v2.4.0):

```rust
// audit_json = { vulnerabilities: {...}, cis_compliance: {...} }
let mut payload = snmp_payload;
if let Some(audit) = audit_json {
    payload["audit"] = audit;  // ← todo iba en 1 POST
}
send_to_server(payload).await
```

Ahora (v2.5.0):

```rust
send_to_server(snmp_payload).await?;  // POST 1

if let Some(audit) = audit_json {
    if let Some(v) = audit.get("vulnerabilities").cloned() {
        match audit_sender::send_audit_payload(&base, token, Vulnerabilities, v, hostname).await {
            Ok(_)  => log::info!("✔ audit/vulnerabilities OK"),
            Err(e) => {
                log::warn!("⚠ audit/vulnerabilities falló, fallback al payload SNMP: {e}");
                snmp_payload["audit"]["vulnerabilities"] = ...; // compat
            }
        }
    }
    if let Some(c) = audit.get("cis_compliance").cloned() {
        // análogo
    }
}
```

### Multi-vendor: 1 POST por dispositivo, todos al mismo server

El motor recorre cada bloque `[[device]]` en `connection.config` y emite su trío
de POSTs. Ejemplo con 3 FortiGates:

```
[1/9] POST /api/relay/data/                       ← FortiGate-VM64 (192.168.10.17)
[2/9] POST /api/relay/audit/vulnerabilities/      ← FortiGate-VM64
[3/9] POST /api/relay/audit/cis/                  ← FortiGate-VM64
[4/9] POST /api/relay/data/                       ← FortiGate-Sucursal (10.0.5.1)
[5/9] POST /api/relay/audit/vulnerabilities/      ← FortiGate-Sucursal
[6/9] POST /api/relay/audit/cis/                  ← FortiGate-Sucursal
[7/9] POST /api/relay/data/                       ← FortiGate-DMZ (172.16.0.1)
[8/9] POST /api/relay/audit/vulnerabilities/      ← FortiGate-DMZ
[9/9] POST /api/relay/audit/cis/                  ← FortiGate-DMZ
```

Cada POST incluye `device_hostname` y `vendor` en el body, por lo que el server
identifica correctamente a qué dispositivo pertenece. **No hay cross-talk** entre
dispositivos: cada uno tiene sus propios `RelayAuditRun`, `RelayVulnerabilityFinding`
y `RelayCisFinding` en la BD.

## Instalación / actualización

### Instalación nueva (primera vez)

```bash
sudo ./install_relay.sh
# Sigue las preguntas interactivas o usa --silent
```

### Actualización (ya tienes relay instalado)

**Paso 1**: Sube el nuevo binario a la VM Debian 12:

```bash
# Desde tu máquina de desarrollo
scp ness-relay-x86_64 update_relay_binary.sh nessuser@<IP_VM>:/tmp/
```

**Paso 2**: En la VM:

```bash
sudo cp /tmp/ness-relay-x86_64 /opt/ness_relay/
sudo chmod 755 /opt/ness_relay/ness-relay-x86_64
sudo md5sum /opt/ness_relay/ness-relay-x86_64
# Debe imprimir: 44a78d0d08a429c2729771ddc32758e5
```

**Paso 3**: Smoke test sin tocar config:

```bash
sudo -u root /opt/ness_relay/ness-relay-x86_64 --probe
# Debe enumerar los dispositivos de connection.config
```

**Paso 4**: Ejecutar una corrida real:

```bash
sudo /opt/ness_relay/ness-relay-x86_64
tail -50 /var/log/ness_relay/ness-relay.out.log
```

Deberías ver en el log:

```
[INFO] POST /api/relay/data/ → 200
[INFO] POST /api/relay/audit/vulnerabilities/ → 200
[INFO] POST /api/relay/audit/cis/ → 200
```

### Actualización con el script automatizado

```bash
sudo ./update_relay_binary.sh /tmp/ness-relay-x86_64
```

El script:
1. Valida MD5 y tamaño del nuevo binario
2. Hace backup del viejo en `/var/log/ness_relay/backups/`
3. Copia el nuevo a `/opt/ness_relay/`
4. Ejecuta `--probe` para verificar que la config carga
5. **NO toca**: connection.config, secrets.env, cron, logs, reports

## Compatibilidad hacia atrás

- Si el server **NO** tiene los endpoints `/api/relay/audit/...` (versión
  anterior a 2.5.0), el agente hace **fallback automático**: anexa el bloque al
  payload SNMP como en v2.4.0. Loguea un warning pero sigue funcionando.
- Si el server **SÍ** los tiene (v2.5.0+), usa el camino dedicado y omite el
  fallback.

Esto significa que **no hay que coordinar versiones** entre agente y servidor
durante el rollout: primero actualiza el server (commits 1-30), luego los
agentes (commit 31+). Cualquier orden funciona.
